# UI Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the merged redesign (branch `ui-polish`) into a CRM a clinic would pay for: correct and readable escalations, a branded shell that works on a phone, and day screens that summarise the day.

**Architecture:** Server components stay as they are; data changes live in `src/lib/` as plain functions with tests; presentation reuses the design tokens in `src/app/globals.css` and the primitives in `src/app/(crm)/_ui.tsx` (`Badge`, `btnPrimary`, `btnSecondary`, `Skel`). No client-side state libraries, no new dependencies, no new routes.

**Tech Stack:** Next.js 16 App Router (server components, server actions), Tailwind v4 tokens in `globals.css`, `node:test`.

**Spec:** the controller's UI audit of 2026-10-13 (below), taken at 1366×860 and ~300px wide, as receptionist and as doctor, on the live dev database.

### Audit findings this plan answers

1. Escalation inbox shows the patient's *latest* message on every card, not the message that caused that escalation (`src/lib/escalations.ts` `last_message` subquery).
2. Escalation reasons are raw internal strings, including a JSON error body (`classifier unavailable: … 400 {"error":…}`).
3. Branding is generic ("Clinic CRM"); the clinic's own name appears nowhere in the shell or on the login page.
4. On a phone, the nav becomes a horizontally scrolling strip with a visible scrollbar ("Escalations" cut off), and every table scrolls sideways, hiding columns.
5. The doctor's "My day" and the clinic calendar are sparse: no summary of the day, no emphasis on who is next, large empty areas.

Out of scope (separate plans): prescription delivery and its copy (docs/02 Meta health-information change — the form still says "sent to the patient on WhatsApp"; do not reword it here), the booking `reason_text` content, CRM booking/reschedule actions, staff management.

## Global Constraints

- No new dependencies. Tailwind classes and existing tokens (`bg-surface`, `text-ink`, `text-ink-2`, `text-ink-3`, `border-line`, `accent`, `danger`, `warn`, …) only — read `src/app/globals.css` first; add a token there rather than a raw hex value in a component.
- Product name in the UI is exactly `Doctor-CRM`. The clinic's name comes from the database (`clinics.name`), never hard-coded.
- Patient health text shown to staff stays as the patient wrote it; reason *labels* are staff-facing summaries and must not interpret clinical content.
- Every page must render without a horizontal page scroll at 375px wide, and keyboard focus must stay visible (existing `:focus-visible` styles).
- Role rules are unchanged: a doctor never sees the escalation inbox; the scoping in `src/lib/patients.ts` and `src/lib/doctor.ts` is not touched.
- Tests via `bash <scratchpad>/runtests.sh [files]` only (sandbox disabled); `npx tsc --noEmit` clean. Every file valid UTF-8 (`tests/source-encoding.test.ts`).
- Commit per task on `ui-polish`, message ending `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. No push.

## Review Focus

- An escalation raised by the first of several messages → its card shows that first message, not a later one (Task 1 test).
- A reason string that matches no known prefix → shown as a neutral "Needs a person" label with the raw text available, never hidden (Task 1 test).
- A clinic whose name is long (40+ characters) → the sidebar and mobile bar truncate with an ellipsis instead of wrapping into the nav (Task 2, checked in the browser).
- A day with zero appointments → summary strip shows zeros and a friendly empty state, not a blank table (Task 4).
- A doctor whose remaining appointments are all in the past → "Next patient" card is absent and the empty-state line says the day's list is done (Task 4).

### Task 1: Escalations that say what happened

**Files:**
- Modify: `src/lib/escalations.ts` (`listEscalations` query; new `describeReason`)
- Modify: `src/app/(crm)/escalations/page.tsx`
- Test: `tests/escalations.test.ts` (create if absent; follow `tests/doctor.test.ts` fixture style)

**Interfaces:**
- Produces:
  - `listEscalations(...)` rows: rename `last_message` → `trigger_message: string | null` = the newest inbound message of that conversation with `created_at <= e.created_at` (same transaction timestamps are equal, hence `<=`).
  - `describeReason(reason: string): { label: string; tone: Tone; detail: string }` — `Tone` from `src/app/(crm)/_ui.tsx` (re-export the type from `src/lib` if the import direction requires it; `src/lib` must not import from `src/app`, so define the tone union in `src/lib/escalations.ts` as `"danger" | "warn" | "neutral"` and make sure it is assignable to `_ui.tsx`'s `Tone`).

`describeReason` mapping, first match wins (prefix match on the stored reason):

| reason starts with | label | tone |
|---|---|---|
| `emergency signal` | `Emergency` | `danger` |
| `clinical question` | `Medical question` | `warn` |
| `repeatedly unreadable` | `Voice note or photo — couldn't read it` | `warn` |
| `repeatedly unclear` / `intent unclear` | `Couldn't understand the request` | `neutral` |
| `classifier unavailable` | `Assistant couldn't process this message` | `neutral` |
| `reply could not be delivered` | `Our reply didn't reach the patient` | `warn` |
| `message could not be processed` | `Message couldn't be processed` | `warn` |
| `reminder could not be delivered` | `Reminder didn't reach the patient` | `warn` |
| anything else | `Needs a person` | `neutral` |

`detail` is the full raw reason.

- [ ] **Step 1: Write the failing tests** in `tests/escalations.test.ts`:
  - `"each escalation shows the message that raised it"` — insert two inbound messages on one conversation, an escalation whose `created_at` sits between them (set explicitly), and a later escalation; `listEscalations` → first row's `trigger_message` is the earlier message, second row's is the later one.
  - `"describeReason gives staff a plain label and keeps the raw text"` — one assertion per table row above, including a JSON-bearing `classifier unavailable: … 400 {"error":…}` → label `Assistant couldn't process this message`, `detail` equal to the input; `"something new"` → `Needs a person` / `neutral`.
- [ ] **Step 2: Run to verify they fail** — runtests on `tests/escalations.test.ts`.
- [ ] **Step 3: Implement** the query change and `describeReason`; on the page, replace the raw "Escalated because: …" line with a `Badge` carrying the label (tone from the result) and a native `<details>` "Details" disclosure holding `detail`; render `trigger_message` where `last_message` was. Add a one-line summary under the page title: `{open} waiting · {emergencies} emergency` (counts from the rows already loaded).
- [ ] **Step 4: Run to verify they pass**, `npx tsc --noEmit` clean.
- [ ] **Step 5: Commit** — `feat(ui): escalations show the message that raised them, in plain words`.
